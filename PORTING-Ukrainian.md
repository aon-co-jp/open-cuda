# open-cuda — Посібник з перенесення (скорочена версія)

> **Примітка**: це скорочений переклад актуальних придатних для
> повторного використання патернів. Детальний історичний журнал
> HANDOFF доступний лише японською в [PORTING.md](PORTING.md) —
> звіряйтеся з ним перед фактичним застосуванням патерну.

Підсумок придатних для повторного використання архітектурних
патернів цього проєкту — на випадок перенесення в інший проєкт.

1. **Трейт `GpuDevice` (дизайн, незалежний від бекенду)**:
   мінімальний контракт у дусі CUDA Runtime API (`alloc`/`free`/
   `memcpy_h2d`/`memcpy_d2h`/`memcpy_d2d`/`launch_kernel`/
   `synchronize`) плюс прапори можливостей
   (`supports_spirv`/`supports_dxil`, за замовчуванням `false`).
   Нові апаратні бекенди реалізують цей контракт і розширюють
   перелік `KernelSource` без порушення сумісності (наприклад,
   `Dxil(Vec<u8>)`).
2. **Дворівневий патерн «мок → реальне залізо»**: Фаза 1
   (мок-пристрій, працює без заліза, перевіряє контракти навіть у
   CI без GPU), Фаза 1.5–2 (реальна реалізація за Cargo-фічею, за
   замовчуванням вимкнена, чесно пропускає себе за відсутності
   реального заліза).
3. **Пастка вирівнювання масивів у HLSL cbuffer**: скалярні масиви в
   `cbuffer` вирівнюються по межі 16 байт — щільно упаковані
   константи Rust/C++ перестають збігатися з розкладкою HLSL
   (реально спричинило баг «вивід залишається відкритим текстом» у
   ядрі ChaCha20). Рішення: окремі скалярні поля (`key0`…`key7`)
   замість оголошення масиву.
4. **Root signature, вбудована в HLSL**: атрибут
   `[RootSignature(...)]`, написаний прямо в шейдері, змушує `dxc`
   вбудувати root signature в DXIL — усуває потребу вручну будувати
   дескриптор root signature в коді Rust/C++. Пряма прив'язка root
   UAV дескрипторів замість descriptor heap.
5. **Перелік адаптерів DXGI для визначення виробника**:
   `D3D12CreateDevice(None, ...)` не дає інформації про виробника й
   обсяг VRAM. `IDXGIFactory1::EnumAdapters1(0)` →
   `DXGI_ADAPTER_DESC1` дає PCIe vendor ID (NVIDIA/AMD/Intel). У разі
   збою безпечно відкочуватися до `None`.
6. **Чесне попередження щодо стиснення/шифрування на GPU**: для
   невеликих payload (розмір мережевого MTU) накладні витрати на
   передачу Host↔Device можуть звести нанівець обчислювальну
   перевагу GPU — перед інтеграцією провести реальні бенчмарки на
   цільовому розмірі payload.
7. **Патерн ядер парності RAID6**: змінна кількість дисків з даними
   як один зчеплений буфер (замість окремих прив'язок на диск).
   Множення в GF(2^8) для Q-parity (Ріда-Соломона) як самостійна
   функція `gf_mul` (множення «по-селянськи», незвідний многочлен
   `0x11D`) усередині шейдера.
8. **Реалізація на GPU без залежності від 64-бітних цілих**:
   64-бітні цілі — опціональна апаратна фіча в DXIL SM6.0. Poly1305
   реалізує парне множення/додавання/зсув 32×32→64 біт лише на
   32-бітних операціях — патерн для перенесення криптографії/
   великих чисел на цілі без гарантії 64-біт.
9. **Стиснення KV-кешу у стилі MLA від DeepSeek-V3**: down-/up-
   проєкція на основі наявної `sgemm`. **Чесне розкриття**: матриці
   проєкції ініціалізовані лише випадково (без навчених ваг) —
   стиснення з втратами; це доводить лише коректність
   обчислювального шляху, а не збереження якості генерації.
10. **Штраф за повторення (у стилі CTRL)**: `logit>0` → `/penalty`,
    `logit<=0` → `*penalty`, застосовується до вже зустрінутих
    токенів перед argmax. `penalty=1.0` — короткий шлях, що точно
    зберігає наявну поведінку `generate()` (без регресій).
    Емпіричне значення за замовчуванням `1.3` — потребує
    перекалібрування під структуру промпту.

**Поточний стан**: Cargo workspace з `opencuda-core`/`opencuda-cpu`/
`opencuda-vulkan`/`opencuda-directx`/`opencuda-blas`/
`open-cuda-bert`/`open-cuda-llm`. `opencuda-directx` реалізований до
Фази 2 (vector_add/matmul/ChaCha20/Poly1305 перевірені на реальному
залізі). Ядра парності RAID6 P/Q додані до `opencuda-vulkan`,
перевірені на реальному залізі. Деталі — у записах HANDOFF у
[CLAUDE.md](CLAUDE.md).
